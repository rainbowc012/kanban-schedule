# 작업 내용 수정

## User-visible outcome

작업 창에서 선택된 작업의 제목·상세 내용·이슈/기능 구분·심각도를 등록 때와
같은 형태의 폼으로 고쳐 저장할 수 있다. 상태(계획/실행/완료)와 일정 구간은
이 기능으로 바뀌지 않는다 — 그건 카드 이동과, 아직 구현되지 않은
[schedule-correction](../../decisions/schedule-correction.md)의 영역이다.

## Approved scope

- 작업 창의 상세 보기에 Delete 옆 Edit 버튼을 추가한다
- Edit을 누르면 등록(New) 폼과 같은 필드 구성(제목, 이슈/기능, 심각도, 상세
  내용)의 수정 폼으로 전환된다. 값은 현재 작업 내용으로 채워져 있다
- 저장하면 작업의 제목·내용·이슈/기능·심각도가 갱신되고 상세 보기로
  돌아간다. 칸반 카드, 달력의 구간 라벨, 주간보고 목록 등 그 작업 제목·
  심각도·구분을 표시하는 모든 화면이 즉시 새 값으로 보인다
- 취소하면 아무 것도 바뀌지 않고 상세 보기로 돌아간다
- 계획·실행·완료 어느 상태의 작업이든 수정할 수 있다. 완료되어 취소선이
  표시된 작업도 예외가 아니다
- 새로고침해도 수정한 내용이 유지된다 (localStorage)

## Out of scope for this spec

| 항목 | 이유 |
|---|---|
| 상태(계획/실행/완료) 변경 | 카드 이동 버튼의 영역. 이 폼에서 상태를 바꾸면 "이동이 곧 기록"이라는 핵심 기제를 우회하게 됨 |
| 일정 구간의 날짜 수정·삭제·되돌리기 | [schedule-correction](../../decisions/schedule-correction.md)에 방향이 결정되어 있으나 아직 구현되지 않은 별도 스펙의 영역 |
| 수정 이력·되돌리기(undo) | 저장 전에는 취소로, 저장 후에는 다시 Edit을 눌러 고치면 되므로 별도 되돌리기 동작을 두지 않음 |

## Acceptance criteria

**Edit 진입**
- 작업을 선택하고 상세 보기의 Edit 버튼을 누르면, 제목·이슈/기능·심각도·
  상세 내용이 현재 값으로 채워진 폼이 나타난다

**저장**
- 값을 고치고 저장하면 폼이 닫히고 상세 보기로 돌아가며, 바뀐 제목·내용·
  이슈/기능·심각도가 그대로 보인다
- 그 작업이 표시되는 다른 화면(칸반 카드, 달력의 구간 라벨, 주간보고
  진행/완료/보류 목록)도 새 값을 즉시 반영한다
- 제목을 빈 값으로 비우면 저장할 수 없다 (등록 폼과 동일한 규칙)
- 상태와 일정 구간은 저장 후에도 그대로다

**취소**
- 값을 고치던 중 취소를 누르면 폼이 닫히고, 고치기 전 값 그대로 상세 보기가
  나타난다

**완료된 작업의 수정**
- 완료 열로 넘어가 취소선이 표시된 작업도 Edit으로 제목·내용·이슈/기능·
  심각도를 고칠 수 있다. 상태는 완료로 그대로 유지된다

**지속성**
- 페이지를 새로고침해도 수정한 제목·내용·이슈/기능·심각도가 유지된다

## Settled constraints and rationale

- 확인 대화상자를 두지 않는다. 저장 전에는 취소로, 저장 후에는 다시 Edit을
  열어 고칠 수 있어 되돌릴 수 있는 동작이기 때문이다 (PRODUCT.md 경험 원칙:
  "되돌릴 수 있는 동작에는 되돌리기를, 되돌릴 수 없는 동작에는 확인을 둔다")
- 완료된 작업도 수정 대상에 포함한다. PRODUCT.md는 "등록·수정·삭제도
  사용자가 한다"고만 하고 상태별 제약을 두지 않으며, "일정 기록은 지워지지
  않는다"는 원칙은 일정 구간에 대한 것이지 제목·내용 같은 작업 속성에는
  적용되지 않는다. 완료 후 발견한 오타나 설명 보완을 고칠 수단이 없으면
  불편하다
- 주간보고와 완료 열은 항상 작업의 현재 값을 실시간으로 읽는 기존 구조를
  그대로 쓴다 (별도 스냅샷을 두지 않음). 그래서 완료 후 심각도를 고치면
  이미 지난 주간보고 화면에서도 새 심각도로 보인다 — 이는 새로 만드는
  동작이 아니라 기존 실시간 반영 구조의 자연스러운 결과다

## Assumptions

- Edit 버튼은 상세 보기에서 Delete 옆에 둔다. 정확한 배치·간격은 구현 시
  기존 디자인 시스템에 맞춰 정한다
- 수정 폼은 등록 폼과 같은 자리(작업 창)에서 전체 폼으로 전환되는 형태를
  쓴다. 별도 모달을 열지 않는다 ("한 주가 한 화면에 있다"는 PRODUCT.md
  경험 원칙과 일관되게, 등록 폼이 이미 같은 패턴을 쓰고 있음)
- 제목 외 필드(이슈/기능, 심각도, 상세 내용)의 유효성 검증은 등록 폼과
  동일하게 없음 — 심각도는 select라 항상 유효한 값이고, 상세 내용은
  비어 있어도 등록 폼처럼 허용한다

## Remaining risks

- 완료된 작업의 심각도·이슈/기능 구분을 나중에 바꾸면, 이미 팀 페이지에
  옮겨 적은 지난 주간보고 내용과 앱 화면상의 값이 어긋날 수 있다. 이 기능은
  앱 화면 자체의 최신 상태를 보여주는 것이 목적이고, 이미 팀 페이지에 옮겨
  적은 과거 텍스트를 소급 수정하는 것은 앱의 책임 밖이다
